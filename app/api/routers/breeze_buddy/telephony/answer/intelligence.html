The product definition

For each workflow, the system studies its runs, identifies where outcomes are being lost and why, suggests changes, and shows whether those changes worked.

This is more than a metrics dashboard. The first product surface should be a Workflow Intelligence page within each workflow. A conversational assistant can be added later as another interface to the same capabilities.

04 · Source facts

Execution and business context foundation

Do not create a second execution ledger. Reuse existing records and ensure the intelligence module can access the following facts through stable contracts.

Fact groupRequired information
Workflow identitymerchant_id, workflow ID, name/status and defined purpose/goal.
Version contextPublished version used by each run. Preserve the admission/execution version even if the workflow changes later.
Run / enrollmentRun or enrollment ID, customer reference where permitted, entry/exit time, terminal status and exit reason.
Node executionNode ID/type, arrival/leave timestamps, outcome, next node, attempts and available error information.
Business outcomeGoal event/key, outcome timestamp, value/revenue if available, attribution window and explicit run-to-outcome linkage.
DimensionsApproved platform/channel and customer segment dimensions that can be safely aggregated.

Data correctness requirements

  • Make ingestion and aggregation idempotent; deduplicate events and handle late arrivals.
  • Do not assume every merchant event belongs to a workflow. Define explicit run/customer/time-window attribution rules.
  • Distinguish workflow completion from business conversion. A run can complete without achieving its business goal.
  • Missing historical node history means unknown, not zero drop-off.
  • Use the workflow version actually used by each execution. Version comparisons are unreliable otherwise.

06 · Time resolution

Hourly and daily analytics

Both are required in the proposed design. They are two time granularities over the same underlying facts—not separate analytics engines or separate diagnostic systems.
GranularityPurposeExample
HourlyRecent monitoring, faster detection and investigation of short-lived changes.A node's delivery failure rate rises sharply in the afternoon.
DailyHistorical trends, stable baselines, longer-term reporting and comparisons.Workflow conversion declines over seven days compared with a previous period.

Storage convention

Use one consistent bucket model. A single aggregate table with bucket_granularity and bucket_start, or separate hourly/daily tables, can both work. Avoid a separate table for every metric.

merchant_id workflow_id workflow_version_id bucket_granularity // 'hour' or 'day' bucket_start entries conversions failures computed_at
  • Compare like with like where possible: same hour-of-day/day-of-week, similar cohort and consistent attribution window.
  • Apply minimum-volume/sample-size safeguards. Label low-volume results as insufficient evidence.
  • Reprocess a bounded recent window to account for late-arriving events.
  • Retain detailed hourly buckets for a shorter period and daily rollups longer. Set exact retention after measuring volume and investigation needs.
07 · Investigation

Monitoring and diagnostic engine

One shared diagnostic capability serves all workflows. Do not implement custom diagnostic code for every workflow or node. Reuse a small set of analysis operations and map problem types to playbooks.

Reusable operationQuestion it answers
Time-series / baselineDid a metric change unusually versus a suitable historical baseline?
Workflow / node funnelAt which step are runs or outcomes being lost?
Path / transitionWhich execution paths are associated with better or worse outcomes?
Error / retry analysisDid errors, delivery failures or retries increase?
Duration / bottleneckDid time spent at a node or between nodes increase?
Version comparisonDid performance change between workflow versions or variants?
Contribution analysisWhich segments, nodes or paths account for the largest share of the observed change?

How a diagnostic investigation runs

  1. Trigger: scheduled monitor, dashboard request or explicit user investigation.
  2. Playbook: a problem type (for example goal_conversion_drop) defines initial operations, required data and conditional follow-ups.
  3. Orchestrator: executes approved, bounded, read-only operations and selects follow-ups from structured results.
  4. Evidence evaluator: checks sample size, baseline suitability, completeness, effect size and alternative explanations.
  5. Finding writer: persists the issue, evidence, limitations and suggested next step.

Example playbook: goal conversion drop

1. Confirm the conversion change against an appropriate baseline. 2. Run workflow and node funnel analysis. 3. Compare relevant segments and execution paths. 4. If failures increased, run error/retry analysis. If dwell time increased, run duration analysis. If a new version was published, compare versions. 5. Rank observed contributors and persist evidence + caveats.
Keep the first orchestrator deterministic. Ordinary application code can route between approved operations. An LLM is optional later; it may help interpret a request or explain structured findings, but it must not generate unrestricted SQL or bypass access controls.
08 · Closed loop

Recommendations and learning

  1. Map findings to supported actions. Recommendations must match node types and configuration options that the workflow editor actually supports.
  2. Attach evidence. Include the finding, affected scope, observed metric and evidence strength.
  3. State the expected outcome. Identify the metric expected to improve and guardrails that must not worsen.
  4. Require human approval initially. Do not automatically mutate live workflows in the first version.
  5. Record the actual change. Link the decision to the newly published workflow version and effective time.
  6. Evaluate after a suitable window. Prefer randomized control/A-B testing where supported.
  7. Store the result. Positive, negative, inconclusive or not implemented. Use outcomes to improve recommendation prioritization.
Evidence discipline: A before/after improvement does not prove the recommendation caused it. Label observational comparisons clearly and account for traffic mix, seasonality, concurrent changes and attribution windows.

Operational requirements

  • Jobs are idempotent and retry-safe; use deterministic bucket keys and upserts.
  • Use existing worker/cron composition and coordination patterns. Add a new queue only if existing capacity requires it.
  • Carry merchant/workflow scope and observability context through every job.
  • Bound diagnostic queries by date range, workflow and row/sample limits; use parameterized SQL.
  • Record job status, duration, rows processed, late data and errors.
  • Version aggregation and diagnostic logic so results can be reproduced and rebuilt.

11 · Trust & safety

Security, correctness and evidence guardrails

  • Every query, aggregate and finding is merchant-scoped. Never mix merchant data in tables, caches or diagnostics.
  • Use approved dimensions and fields; do not expose customer-level details in shared dashboard summaries.
  • Read source data through owning module contracts. Intelligence owns and writes only its own tables.
  • All SQL is parameterized and bounded. No LLM-generated unrestricted SQL.
  • Separate observed fact, statistical association, likely contributor and causal proof in findings.
  • Show sample size, date range, baseline and data-quality caveats with every material finding.
  • Do not interpret missing data as zero or incomplete history as a confirmed drop-off.
