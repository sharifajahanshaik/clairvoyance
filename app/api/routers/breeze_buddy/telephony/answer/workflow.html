01 · Executive summary

What are we proposing?

Workflow Intelligence is an intelligent capability that uses workflow definitions, execution data, historical patterns, and business outcomes to understand, analyze, and continuously improve workflows across their lifecycle. It helps identify potential improvements before execution, make informed decisions during execution, and investigate execution results afterward to understand what worked, where outcomes were lost, why they happened, and how workflows can be optimized to achieve better business outcomes.

What happened?

Analytics

Measure outcomes, paths, drop-offs, retries, delays and changes across workflow executions.

Deterministic
Why did it happen, and what can improve?

Diagnostics

Investigate meaningful patterns, gather evidence, identify contributing factors and produce improvement recommendations.

Agent-driven investigation
Proposed direction: deterministic analytics identifies meaningful observations; an LLM agent investigates them using approved tools and produces evidence-backed findings and improvement recommendations. The LLM is invoked selectively, not for every event, call or enrollment.
02 · Product context

Use existing platform capabilities and add the intelligence layer

The platform already manages workflow definitions, enrollments, events, execution history and call-level evaluation. Workflow Intelligence uses these existing capabilities and adds cross-execution analysis, diagnosis and improvement recommendations. It is an integrated capability within the platform, not a separate system that replaces existing functionality.

Existing capabilities to consume

  • Workflow definitions, versions and configured goals/outcomes.
  • Enrollment records and workflow execution/step history.
  • Events and topics, which vary by workflow and merchant.
  • Call-level topic and outcome evaluation results.
  • Relevant customer and merchant context through existing services.

What Workflow Intelligence adds

  • Population-level measurement of workflow performance.
  • Detection of meaningful changes and outcome leakage.
  • Evidence-driven investigation of possible contributing factors.
  • Evidence-backed workflow improvement recommendations.
  • A way to assess whether recommended changes actually helped, when evaluation data is available.
Boundary: this proposal does not rebuild the workflow runtime, event ingestion, CRM, call evaluation or Centralised Memory. Memory remains owned by its existing team; Workflow Intelligence may consume relevant context through an agreed interface.
03 · Intelligence scope

One platform, multiple possible scopes

The long-term platform can support different scopes of intelligence. The first release should focus on workflow-level intelligence. Designing reusable contracts now can reduce future duplication, but it does not mean implementing all scopes in the MVP.

MVP

Workflow-level

How is this workflow performing, where are outcomes lost, and how can it improve?

Studies many enrollments and executions over a defined period.

Future

Node-level

How is a particular step behaving, and what should change about it?

Can reuse node-level metrics and diagnostic capabilities; runtime decisions are a separate extension.

Future

Customer-level

What action is suitable for this particular customer?

Needs customer history/context and potentially real-time decisioning. It is not just a workflow report filtered by customer.

Future

Merchant-level

What is happening across this merchant's workflows and business outcomes?

Needs cross-workflow aggregation, merchant objectives and trade-off reasoning.

These scopes are not a mandatory execution chain. They are different analytical/decision contexts that may share data foundations, tools, evidence formats and reasoning capabilities.

04 · Workflow lifecycle

Pre, current and post workflow

These describe when intelligence is used in the workflow lifecycle. They are not three separate intelligence engines.

Pre-workflow

Before execution

Use previously learned findings to help configure a workflow: retry strategy, timing, branching or other settings.

Future use: intelligence-informed workflow design.

Current workflow

During execution

The existing workflow runtime processes events, evaluates conditions and executes actions. Future extensions may consume intelligence for runtime decisions.

MVP boundary: do not add an LLM call to every event or enrollment.

Post-workflow

After/alongside executions

Study accumulated executions, detect outcome gaps, diagnose contributing factors and recommend improvements.

MVP focus: build this first.

06 · Architecture alternatives

Two ways to build Workflow Intelligence

Both approaches can consume the same source data and produce findings. Their main difference is who decides the investigation path: predefined application logic or an adaptive agent.

Approach A

Rule-Based Workflow Intelligence

Investigation paths are explicitly designed in application logic.

Analytics observatione.g. conversion declined
↓
Rule / condition matchingif retry drop-off rises → run retry analysis
↓
Predefined investigation sequenceretry metrics → time comparison → result
↓
Rule-based recommendation mappingif pattern X → suggest option Y

Advantages

  • Predictable, testable and easier to constrain.
  • Low and predictable LLM cost; can run without LLM.
  • Good for known, stable and repetitive diagnostic patterns.

Limitations

  • Investigation paths must be anticipated and maintained.
  • Interacting causes and unfamiliar patterns are difficult to handle.
  • New cases require new rules and mappings.
  • Can become a large collection of analytics checks rather than adaptive diagnosis.
Risk: the system may identify what changed, but struggle to investigate an unexpected combination of factors without another predefined rule.
Approach B

Agent-Based Workflow Intelligence

An LLM agent dynamically chooses which approved evidence to gather and what to investigate next.

Analytics observatione.g. conversion declined
↓
LLM diagnostic agentreviews observation and available tools
↓
Agent selects investigation toolcohort comparison, retry history, version comparison…
↻
Evidence returned to agentagent decides whether more evidence is needed
↓
Structured findingsevidence, hypotheses, confidence, limitations

Advantages

  • Can adapt the investigation to intermediate findings.
  • Can combine evidence across different workflow dimensions.
  • Handles less predictable diagnostic questions better.
  • New tools can expand capability without hardcoding every path.

Limitations

  • LLM cost and latency vary with investigation complexity.
  • Requires strict tool permissions, budgets and output validation.
  • Must prevent unsupported causal claims or repetitive investigation loops.
  • Needs evaluation against known cases to establish reliability.
Key idea: predefined tools are acceptable; predefined investigation sequences for every possible issue are not required. The agent selects tools dynamically within controlled boundaries.

07 · Recommended direction

Recommended architecture: analytics + agent-driven diagnosis

Use deterministic analytics for measurement and observation detection, and an agent for adaptive investigation. The diagnostic findings can include evidence-backed improvement recommendations.

Deterministic

Analytics Engine

Calculates metrics, compares cohorts, applies thresholds, validates sample sizes and detects observations.

No LLM needed for calculations.

Agent-driven

Diagnostic Engine

Agent chooses tools and investigation sequence; controlled tools fetch evidence; the agent interprets returned evidence.

LLM used selectively for investigation.

Diagnostic Engine: how agentic reasoning stays controlled

Shared tool capabilities

  • Retrieve workflow structure and version information.
  • Inspect node execution history and drop-offs.
  • Compare cohorts, time windows and workflow versions.
  • Inspect outcome distributions and retry behavior.
  • Analyze timing, duration and execution details.

These are conceptual tool capabilities, not confirmed API names.

Agent control and safety

  • Allowlisted tools with strict input/output schemas.
  • Tenant, merchant, workflow and time-window scope enforcement.
  • Limits on iterations, tool calls, data volume, tokens and runtime.
  • Read-only investigations for the MVP.
  • Evidence references, provenance and auditable tool calls.
  • Stop when evidence is sufficient or unavailable; report uncertainty.
Why this is intelligence: the platform does more than display metrics. It identifies an outcome gap, adaptively investigates relevant evidence, develops and qualifies explanations, and identifies evidence-backed opportunities to improve outcomes.

09 · Invocation, cadence and cost

When does the system run?

The system should not invoke an LLM after every raw event, call or enrollment. Data is collected continuously; analytics runs on a schedule or incrementally; diagnostics runs only when there is something meaningful to investigate.

Continuous

Data capture

Existing runtime persists events, enrollments, execution and evaluation results. No intelligence LLM call.

Periodic

Analytics

Hourly or configured intervals; compute metrics and detect observations deterministically.

Conditional

Diagnostics

Start an LLM investigation when an observation passes the investigation gate.

What qualifies as an investigation trigger?

Criteria should be configurable and validated, not treated as universal hard-coded thresholds. Examples:

  • A material change in a configured workflow goal metric.
  • A sustained increase in drop-offs or execution failures.
  • A notable change in retry effectiveness or outcome mix.
  • A newly emerging path or cohort pattern worth understanding.
  • A workflow-version comparison that shows a meaningful difference.

Use sample-size checks, minimum effect/materiality, persistence, novelty and duplicate-investigation suppression. A small fluctuation should not automatically create an LLM investigation.

Cost model

Not proportional to enrollment count

100,000 enrollments do not mean 100,000 agent calls. Analytics processes the population; an investigation is triggered for a meaningful workflow-level observation.

Cost depends on investigation complexity

Main drivers are number of investigations, LLM reasoning iterations, tool calls, context size, token usage and model choice.

Cost controls: deterministic analytics first; deduplicate observations; bound tool calls/iterations and data returned; reuse prior findings where the evidence has not materially changed; invoke diagnostics selectively. Actual cost should be benchmarked using representative merchant workloads before committing to an estimate.

10 · Architecture review

Decisions to align on before implementation planning

This document is intended to get agreement on the architectural direction. It is not yet a technical implementation plan.

  1. Scope: agree that the first release is workflow-level, post-execution intelligence.
  2. Architecture: agree on deterministic analytics and agent-driven diagnostics that produce evidence-backed findings and improvement recommendations.
  3. Investigation model: agree that rules determine whether an investigation should start, while the agent can dynamically decide how to investigate.
  4. Invocation: agree that the LLM is not called per event/enrollment and is triggered selectively from meaningful observations.
  5. Data ownership: agree to consume existing execution/evaluation data and avoid rebuilding workflow runtime or Centralised Memory.
  6. Safety: agree on bounded, read-only diagnostic tools for the MVP and evidence-backed findings with explicit uncertainty.
  7. Extensibility: agree to keep shared contracts reusable for future node, customer and merchant scopes without implementing them now.
After architecture review: prepare the implementation plan covering verified source tables/fields, data retrieval, metric definitions, tool contracts, service boundaries, storage schema, scheduling/triggering, evaluation, rollout and cost benchmarking.
